8.0 Architectural Overview
(All text below is preserved verbatim from your earlier draft.)
The QueryBook system is implemented as a unified, multidomain architecture designed to
support ingestion, semantic structuring, retrieval, provenance, licensing, assessment, and
user experience workflows within a single coherent platform. The architecture is intentionally
monolithic in deployment structure while modular in internal design. All domains execute within
a single deployable unit, sharing memory, configuration state, and the internal event bus. This
design eliminates inter service network latency, ensures atomic cross domain transactions, and
simplifies operational monitoring, deployment, and upgrade management.
QueryBook features an architecturally open, flexible deployment design. It is source agnostic
and storage agnostic, operating over relational databases, graph stores, document stores, and
is compatible with all digital readers. The system’s domain modules feature selectable
application and deployment options. The architecture is optimized for both large scale cloud
deployments and extremely low resource embedded deployments. The system is deployed as a
single executable process, whether in a full server class enterprise configuration or in a
reduced backend embedded configuration requiring as little as 4 MB of memory on low power
devices.
In the full configuration, the process connects to external relational, graph, and vector database
servers. In the embedded configuration, all three storage backends are instantiated as
embedded libraries within the same process address space. The Deployment Configuration
Manager in Domain 14 selects and configures the backend type for each of the three storage
layers at startup, presenting an identical Storage Abstraction Layer interface to all domains
regardless of backend type.
The QueryBook system is organized into fifteen specialized functional domains, grouped into
three conceptual layers:
● Layer 1 — Content Ingestion and Normalization (Domains 1–2)
● Layer 2 — Universal API Gateway and RBAC (Domain 15)
● Layer 3 — Knowledge Container and Fact Store (Domain 3)

2
The remaining twelve domains (4–14) consume Fact Units from Layer 3 and produce outputs
such as responses, assessments, provenance manifests, NFT tokens, analytics reports, and UI
data.
The Fact Store serves as the universal semantic substrate shared by all fifteen domains. Every
domain that produces knowledge writes to it exclusively through the Write API, and every
domain that consumes knowledge reads from it exclusively through the Read API. This ensures
a consistent, transactionally unified view of the system’s knowledge state.
Asynchronous coordination among domains is achieved through an internal event bus, an
in process publish subscribe router. When a domain completes a significant operation, it
publishes an event message. Other domains subscribed to that event type receive and process
it accordingly.
8.0A Core Technology Overview
(All text below preserved verbatim.)
Fact Unit Architecture
The fundamental data primitive of the QueryBook system is the Fact Unit (FU), an atomic,
language neutral, immutable semantic triple stored in the Fact Store. Each Fact Unit encodes a
single verifiable assertion in the form:
(subject_entity_id, predicate_id, object_entity_id)
All components are language neutral identifiers resolved through the Ontology Registry and the
FQL Predicate Library. Fact Units are immutable; revisions create new versions linked through a
version chain.
QueryBook Format (QBF)
The QBF is the normalized content container that standardizes all supported source
formats—PDF, EPUB, DOCX, HTML, Markdown, video transcripts, audio transcripts—into a
single canonical structure. It contains normalized text blocks, structural metadata, qbf_id, DPH,
ingestion timestamp, operator identity, and version number.
Hybrid Storage Architecture
Every Fact Unit is simultaneously stored in:

3

● A relational schema
● A property graph schema
● A vector embedding index
Deterministic Provenance
Every response is cryptographically bound to the exact Fact Units that produced it.
Book Contents Limited Query (BCLQ)
BCLQ guarantees that responses are derived exclusively from content the user has licensed.
Confidence Scoring Engine (CSE)
The CSE evaluates every candidate triple using four weighted signals.
Ontology Classification
Each Fact Unit is classified against a hierarchical concept ontology.
Language Neutral Multilingual Support
All knowledge is stored in language neutral identifiers. Natural language rendering occurs at
response time.

[001] 8.1.1 — Source Format Adapters
The system includes a plurality of Source Format Adapters configured to ingest heterogeneous
digital and physical content formats, including but not limited to PDF, EPUB, HTML, DOCX,
XML, scanned images, and proprietary publisher formats. Each adapter normalizes structural

[002] 8.1.2 — Source Acquisition Record
A Source Acquisition Record (SAR) is generated for each ingested artifact. The SAR captures
acquisition metadata including source_uri, acquisition_timestamp, publisher_id, edition_id,
rights_scope, checksum, and ingestion_operator_id. The SAR is immutable and serves as the
authoritative provenance anchor for all downstream processing, including Fact Unit generation
and licensing enforcement.

[003] 8.1.3 — Unicode Normalization
The Unicode Normalization subsystem converts all textual content into a canonical Unicode
form (NFC), resolving diacritics, ligatures, multi codepoint sequences, and platform specific
encodings. The subsystem ensures deterministic text comparison, tokenization, and semantic
extraction across heterogeneous sources and languages.

5
[004] 8.1.4 — Whitespace Normalization
Whitespace Normalization removes redundant whitespace, collapses multi space sequences,
standardizes line breaks, and eliminates non semantic spacing artifacts introduced by OCR,
PDF extraction, or publisher formatting. The subsystem preserves semantically meaningful
spacing such as paragraph boundaries, table delimiters, and inline formula spacing.

[005] 8.1.5 — Paragraph Reconstruction
The Paragraph Reconstruction engine identifies paragraph boundaries using structural cues,
indentation patterns, linguistic heuristics, and layout metadata. It reconstructs paragraphs from
fragmented line sequences, ensuring that downstream semantic segmentation and extraction
models operate on coherent textual units.

[006] 8.1.6 — Table Reconstruction
The Table Reconstruction subsystem detects tabular structures, extracts cell boundaries,
resolves merged cells, and reconstructs logical row column relationships. It outputs a
normalized table representation with cell level metadata, enabling accurate extraction of
structured relationships and numerical data.

[007] 8.1.7 — Figure Extraction
The Figure Extraction engine identifies embedded figures, diagrams, and illustrations. It extracts
associated captions, alt text, and figure references, assigning each figure a unique figure_id.
Extracted figures are stored in the Media Repository and linked to their originating QBF and
structural location.

[008] 8.1.8 — Equation Extraction
The Equation Extraction subsystem identifies mathematical expressions in LaTeX, MathML, or
image based formats. It converts recognized equations into a normalized symbolic
representation and associates each equation with its surrounding textual context and structural
location.

6
[009] 8.1.9 — Structural Segmentation
Structural Segmentation partitions the ingested content into hierarchical units including
chapters, sections, subsections, paragraphs, tables, figures, and equations. Each structural unit
receives a stable structural_id and is recorded in the QBF structural graph for downstream
alignment and retrieval.

[010] 8.1.10 — Semantic Segmentation
Semantic Segmentation classifies textual spans into semantic categories such as definitions,
theorems, examples, proofs, explanations, and learning objectives. The subsystem uses
transformer based classifiers and rule based heuristics to assign semantic labels with
associated confidence scores.

[011] 8.1.11 — Media Extraction
The Media Extraction subsystem identifies and extracts embedded multimedia assets including
images, audio, and video. Each asset is assigned a media_id, stored in the Media Repository,
and linked to its structural context. Metadata such as resolution, duration, and format are
recorded for downstream rendering.

[012] 8.1.12 — OCR Pipeline
The OCR Pipeline processes scanned documents and image based content using multi stage
recognition, including text detection, line segmentation, character recognition, and
language specific post correction. OCR outputs are merged with layout metadata to preserve
structural fidelity.

[013] 8.1.13 — Formula Recognition
The Formula Recognition subsystem identifies mathematical expressions within OCR outputs or
embedded images. It reconstructs symbolic structure using neural sequence models and
outputs normalized MathML or LaTeX representations linked to the originating structural unit.

[014] 8.1.14 — Rights Tagging
Rights Tagging assigns rights metadata to each structural unit, including territorial restrictions,
edition restrictions, institutional overrides, and license expiration parameters. Rights tags
propagate to all derived Fact Units and govern retrieval, rendering, and export operations.

[015] 8.1.15 — Edition Lineage Resolver
The Edition Lineage Resolver computes relationships among multiple editions of the same work
using structural similarity, semantic overlap, and Fact Unit alignment. It assigns each QBF an
edition_lineage_id and edition_sequence_number, enabling edition aware retrieval, analytics,
and licensing enforcement.

[016] 8.1.16 — QBF Assembly
QBF Assembly constructs the QueryBook File (QBF) object by integrating structural
segmentation, semantic segmentation, extracted media, equations, tables, and rights metadata.
The QBF serves as the canonical container for all downstream extraction and Fact Unit
generation processes.

[017] 8.1.17 — DPH Computation
The Document Provenance Hash (DPH) is computed over the normalized content, structural
graph, rights metadata, and media assets. The DPH provides a tamper evident fingerprint used
for provenance verification, NFT minting, and cross edition alignment.

[020] 8.1.20 — Ingestion Error Logging
The Ingestion Error Logger records anomalies encountered during ingestion, including

[021] 8.2.1 — Named Entity Recognition
(NER) Engine
The NER Engine identifies and classifies entity mentions within normalized text spans. It uses
transformer based sequence labeling models trained on multi domain corpora to detect entities
such as persons, locations, organizations, quantities, dates, and domain specific constructs.
Each detected entity is assigned an entity_span_id, entity_type, confidence score, and structural
reference. The NER Engine outputs token aligned spans suitable for downstream predicate
extraction and entity resolution.

10

[022] 8.2.2 — Predicate Extraction
Engine
The Predicate Extraction Engine identifies predicate phrases and relational cues within
sentences. It uses dependency parsing, semantic role labeling, and transformer based
classifiers to extract predicate candidates. Each predicate is assigned a predicate_span_id,
predicate_type, and associated argument placeholders. Extracted predicates serve as the
backbone for Fact Unit assembly.

[023] 8.2.3 — Relation Extraction
Ensemble
The Relation Extraction Ensemble applies multiple relation extraction models, including
supervised classifiers, distant supervision models, and transformer based relation predictors.
Each model outputs candidate triples with associated confidence scores. The ensemble
aggregates model outputs using weighted voting, model reliability profiles, and corroboration
counts to produce a unified relation set.

[024] 8.2.4 — Coreference Resolution
Engine
The Coreference Resolution Engine identifies and links mentions referring to the same
underlying entity across sentences and paragraphs. It uses span pair scoring, clustering
algorithms, and contextual embeddings to produce coreference chains. Each chain is assigned
a coref_chain_id and is used to unify entity references during Fact Unit assembly.

[025] 8.2.5 — Semantic Role Labeling
(SRL)
The SRL subsystem assigns semantic roles (e.g., AGENT, PATIENT, THEME, LOCATION,
TIME) to arguments associated with each predicate. It uses transformer based SRL models and

11
dependency based heuristics to produce structured argument frames. SRL outputs are used to
populate Fact Unit fields and validate predicate argument completeness.

[026] 8.2.6 — Multi Hop Inference
Engine
The Multi Hop Inference Engine identifies implicit relationships requiring reasoning across
multiple sentences or structural units. It uses graph based inference, contextual embeddings,
and rule based templates to infer relationships not explicitly stated in a single sentence.
Multi hop inferences are flagged with inference_type and inference_confidence metadata.

[027] 8.2.7 — Pedagogical Marker
Extraction
The Pedagogical Marker Extraction subsystem identifies instructional cues such as “key idea,”
“important,” “definition,” “example,” “theorem,” and “note.” These markers are used to enrich
Fact Unit metadata and support downstream assessment generation, reader experience, and
curriculum alignment.

[028] 8.2.8 — Fact Unit Assembly Engine
The Fact Unit Assembly Engine constructs Fact Units by combining entity spans, predicate
spans, argument roles, and contextual metadata. Each Fact Unit includes subject_id,
predicate_id, object_id, concept_path, provenance references, and confidence scores. The
assembly engine validates structural completeness and semantic coherence before admission
into the Fact Store.

[029] 8.2.9 — Fact Unit Metadata Fields
Each Fact Unit includes standardized metadata fields including fu_id, qbf_id, structural_id,
entity_ids, predicate_id, concept_path, language_code, edition_id, rights_tags, model_outputs,
and provenance hashes. Metadata fields ensure consistent retrieval, filtering, and analytics
across domains.

12

[030] 8.2.10 — Confidence Scoring
Engine
The Confidence Scoring Engine computes a composite confidence score for each Fact Unit
using model agreement, corroboration counts, entity predicate compatibility, semantic
coherence, and structural alignment. Confidence scores determine admission thresholds,
low confidence routing, and analytics weighting.

[031] 8.2.11 — Low Confidence Triple
Register
The Low Confidence Triple Register stores Fact Units whose composite confidence score falls
below the admission threshold but above the discard threshold. Each entry includes fu_id,
qbf_id, model disagreement patterns, and diagnostic metadata. These triples are excluded from
retrieval but retained for model retraining and ontology refinement.

[032] 8.2.12 — Ontology Classification
Engine
The Ontology Classification Engine maps extracted entities and predicates to canonical
ontology nodes. It uses embedding similarity, alias sets, disambiguation rules, and multilingual
canonical strings to assign concept_ids and predicate_ids. Classification outputs include
confidence scores and alternative candidates.

[033] 8.2.13 — Concept Path Assignment
Engine
The Concept Path Assignment Engine assigns each Fact Unit a concept_path derived from the
ontology DAG. It computes the most specific path consistent with the Fact Unit’s semantic
content, structural context, and prerequisite relationships. Concept paths support retrieval,
assessment generation, and analytics.

13
[034] 8.2.14 — Version Chain Linking
