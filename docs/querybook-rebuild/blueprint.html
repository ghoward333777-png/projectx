Design principles

One window, one start

Everything opens from one double-click into one window. The four apps and the Control Panel become areas of that window instead of five programs.

Ask is the front door

The home screen is a single question box. Every answer shows its sources, a verified / contradicted / unknown badge, and whether it is past, present or projected.

Show only your role

A Reader, Author, Instructor or Admin switch hides what you don't use. Admin areas (harvesting, security, system) never clutter reading.

No dead buttons

A feature appears on screen only when it works. Planned features live on a Roadmap page, never as controls that do nothing.

Consent before sensing

Camera, microphone, voice analysis and voice ID each need a visible, per-session switch, with an indicator while on.

Math you can trust

Every formula carries a "proved" mark when its Lean proof passes, and the same code runs in Python today and Rust later.

Build stages

Each stage ends in a working QueryBook.zip with Python inside: unzip, double-click, use it. Nothing that works today is removed at any stage. Each stage also moves its logic into the Rust-ready core and proves its formulas in Lean before it ships.

Formula math: Rust-ready and Lean-verified

The review found a formula or numeric rule in features, and of them can be stated and proved in Lean 4. Each one becomes a pure function in the core, with three things that must agree:

The Python function

Pure, fully typed, no reflection, checked by the Rust-compatibility test on every build.

The Rust port

Same signature, same results, checked against shared test vectors on every build.

The Lean proof

States the rule (bounds, monotonicity, thresholds) and proves it. The build fails if a proof fails or if the Python behaviour drifts from the Lean examples.

Your decisions

Three choices shape the build. My recommendation is in bold for each; the build starts with these unless you say otherwise.

1. When the registry and today's code disagree

The review found about 30 places, for example voice ID promising anti-spoofing it doesn't do, the camera storing people it should discard, and learning formulas that differ from the registry.

Recommendation: the registry rule wins wherever it protects safety, privacy or truth; the code's tested constants win where the registry gives no number.

2. Features on hold (34)

Robot and equipment control, vehicle monitoring, the "offensive" security posture, smell and haptic hardware, VR commerce, and blockchain/NFT certificates (the registry both declines and builds them).

Recommendation: keep them out of the build until you decide each one; robot control only ever after its safety rules exist.

3. One window or five programs

Today you start five programs. The design puts them in one window with areas.

Recommendation: one window, one start file. Each area can still run on its own for testing.
